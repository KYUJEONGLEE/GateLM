# PII v0.1.1 추론 동시성 검증

## 1. 결론

현재 운영 기본값은 `AI_SERVICE_AI_SAFETY_MAX_CONCURRENT=1`로 유지한다.

동시성 2는 동시성 1보다 처리량이 약 61.1% 높았고 p99도 100ms 이내였지만, 3,000건 중 100ms 초과 요청이 13건 있었다. 이번 gate는 초과 요청이 한 건도 없어야 자동 후보로 인정하므로 어느 동시성도 strict gate를 통과하지 못했다. 따라서 동시성 2는 후속 검증 후보일 뿐 현재 기본값으로 승격하지 않는다.

동시성 4부터는 처리량이 늘어도 p95와 p99가 급격히 악화됐다. 요청마다 ONNX 내부 스레드 4개를 사용하는 상태에서 요청 동시성까지 높이면 CPU를 두고 경쟁하는 실행 단위가 많아지기 때문이다. Pintos에서 배운 관점으로 보면 실행할 일이 많아졌지만 실제 CPU 수는 그대로여서, 스케줄링 경쟁과 대기 시간이 꼬리 지연으로 나타난 경우다.

## 3. Direct inference 측정

50개의 합성 case를 메모리에서만 렌더링했다. 각 동시성 수준을 1,000건씩 3회 교차 순서로 실행했으며, 모든 결과를 순차 실행 기준과 비교했다.

| 동시성 | 처리량 (RPS) | p50 | p95 | p99 | 100ms 초과 | 오류 | 출력 불일치 | CPU 사용률 | 요청당 context switch |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 56.529 | 6.913ms | 64.654ms | 76.651ms | 10 / 3,000 | 0 | 0 | 29.277% | 597.576 |
| 2 | 91.092 | 7.532ms | 84.322ms | 94.798ms | 13 / 3,000 | 0 | 0 | 43.439% | 345.836 |
| 4 | 119.302 | 10.639ms | 135.274ms | 161.064ms | 499 / 3,000 | 0 | 0 | 57.614% | 178.409 |
| 8 | 134.182 | 11.257ms | 263.101ms | 322.735ms | 600 / 3,000 | 0 | 0 | 67.056% | 105.994 |
| 16 | 149.031 | 10.206ms | 475.585ms | 588.586ms | 658 / 3,000 | 0 | 0 | 68.981% | 67.332 |
| 32 | 165.069 | 10.934ms | 833.286ms | 1,025.660ms | 1,070 / 3,000 | 0 | 0 | 79.148% | 54.098 |

### 해석

- 모든 18,000건에서 추론 오류와 순차 기준 대비 출력 불일치는 없었다.
- 동시성 2는 동시성 1보다 처리량이 61.1% 증가했지만 p95는 30.4%, p99는 23.7% 늘었다.
- 동시성 4는 동시성 1보다 처리량이 약 111.1% 증가했지만 100ms 초과 비율이 16.6%였고 p99가 161.064ms까지 증가했다.
- 동시성 32는 처리량이 가장 높았지만 p99가 1초를 넘었다. 평균 처리량만 보고 선택하면 사용자 한 명이 오래 기다리는 요청을 크게 늘릴 수 있다.
- Windows process context switch 값은 동시성이 높아질수록 요청당 감소했다. 고동시성이 더 짧은 시간에 전체 작업을 끝낸 영향도 포함되므로, 이 값만으로 동시성이 높을수록 context switch 비용이 커졌다고 주장할 수 없다. 이번 과도한 동시 실행의 주된 근거는 CPU 사용률 상승과 p95/p99 악화다.

## 4. HTTP admission gate 측정

전체 합성 corpus 50건 중 KoELECTRA 대상 타입이 포함된 21건을 고른 뒤, 원문을 저장하지 않는 in-memory preflight에서 실제 hybrid 실행과 KoELECTRA 기여가 확인된 7건만 사용했다.

process-local capacity를 1로 두고, 8개 요청을 동시에 보내는 wave를 20회 실행했다.

| 항목 | 결과 |
|---|---:|
| 총 요청 | 160 |
| 정상 처리 200 | 20 |
| 즉시 과부하 503 | 140 |
| 기타 상태·transport 오류 | 0 |
| 오류 응답 계약 불일치 | 0 |
| hybrid 실행 유지 | 20 / 20 |
| KoELECTRA 기여 확인 | 20 / 20 |
| 성공 응답 p50 / p95 / p99 | 18.955ms / 165.765ms / 180.205ms |
| 503 응답 p50 / p95 / p99 | 6.466ms / 23.882ms / 27.170ms |
| 다음 wave 슬롯 복구 | 통과 |

이 결과는 요청을 무한히 줄 세우지 않고, 수용할 수 없는 요청을 sanitized `503 sidecar_unavailable`로 빠르게 돌려보내는 동작을 증명한다. 단건과 배치는 같은 process-local gate를 공유하며, 예외나 취소 뒤에도 `finally`에서 슬롯을 반환한다.

## 5. 적용 결정

1. process-local 기본 동시성은 1로 유지한다.
2. 단건과 배치 요청은 같은 gate를 공유한다.
3. capacity가 가득 차면 queue를 늘리지 않고 retry 가능한 sanitized 503을 반환한다.
4. 동시성 2는 4-vCPU Linux 환경에서 다시 검증할 후보로만 기록한다.
5. 동시성 값을 높일 때는 RPS만 보지 않고 p95, p99, deadline 초과율과 출력 동일성을 함께 확인한다.

## 6. 한계와 후속 검증

- 이번 direct 측정 호스트는 CPU 8개를 사용할 수 있어 목표 AWS 4-vCPU 환경과 다르다.
- HTTP 측정은 FastAPI route와 실제 두 ONNX 모델을 사용했지만, socket 대신 process 내부 ASGI transport를 사용했다.
- Uvicorn worker가 여러 개인 경우와 여러 replica의 합산 동시성은 검증하지 않았다.
- Gateway가 실제 network 503을 받고 regex-only 결과로 fallback하는 부하 E2E는 아직 남아 있다.
- strict gate는 동시성 1도 통과하지 못했다. 목표 환경에서 같은 3회 측정을 반복하기 전에는 성능 개선 수치로 production 승격을 주장하지 않는다.
